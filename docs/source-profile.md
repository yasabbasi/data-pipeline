# Source profile: thelook_ecommerce

Read-only profile of `bigquery-public-data.thelook_ecommerce`, taken 2026-11-12 with
`scripts/profile-thelook.sh` (queries in [`sql/profile/`](../sql/profile/)). The source is
synthetic and refreshed daily, so exact counts drift; the shapes below are what the pipeline
relies on.

## Schema

- Every column the pipeline ingests exists with the type in
  `src/data_pipeline/sources/thelook/tables.py`.
- BigQuery marks **all** columns nullable, including keys, so not-null checks are needed.

## The daily refresh regenerates history

A second profile a day later (2026-11-13) showed the refresh rewrites the past as well as
adding a new day:

| | 2026-11-12 | 2026-11-13 |
|---|---:|---:|
| orders | 125,183 | 124,829 (a new day of 1,310 orders, yet 354 fewer in total) |
| earliest order | 2019-01-12 07:50 | 2019-01-05 11:15 |
| order_items | 181,239 | 181,106 |
| earliest user | 2019-01-02 00:19 | 2019-01-02 01:00 |

Incremental ingestion assumes rows older than the lookback window don't change. On this
source, that holds only between two runs in the same refresh. So live runs use
`--full-refresh` (`make run`), and an incremental run first compares the row count and
key sum of the history it won't re-read against the source and refuses to continue if
they differ.

## Order items

| Status | Items | `shipped_at` set | `delivered_at` set | `returned_at` set |
|---|---:|---:|---:|---:|
| Shipped | 54,637 | all | none | none |
| Complete | 45,063 | all | all | none |
| Processing | 36,080 | none | none | none |
| Cancelled | 27,294 | none | none | none |
| Returned | 18,165 | all | all | all |

- `delivered_at >= shipped_at` and `returned_at >= delivered_at` always hold.
- `shipped_at < created_at` for 35,679 items (30% of shipped items): the item's
  `created_at` is not a reliable sale time.
- An item's `created_at` ranges from 4 hours before its order's to 4 days after (median
  0.45 hours before; p99 96 hours after), so 81,817 items (45%) fall on a different UTC
  day than their order.
- Measured from the order instead, the lifecycle is clean: `shipped_at` is never before
  the order's `created_at` and always equals the order's `shipped_at`.
- `sale_price` is always > 0. Item status always equals its order's status, and
  `orders.num_of_item` always equals the order's item count.
- Returns arrive within 10.7 days of the order (p99 9.6 days); none later than 14 days.

## Referential integrity

No orphans: every item has an order and a product, every product a distribution center,
every order a user. 26 product categories, none null.

## Events

| Event type | Events |
|---|---:|
| product | 842,781 |
| department | 592,978 |
| cart | 592,625 |
| purchase | 181,239 |
| cancel | 124,550 |
| home | 87,709 |

- Every `product` event's `uri` matches `/product/<id>`.
- 46% of events have no `user_id` (guest sessions).
- 681,239 sessions, all with a product view; 181,239 contain a purchase, one per order
  item (purchases = sessions with a purchase = order items).
- Only purchase events are ever future-dated (1,146 in a re-run; views and carts: 0). A
  purchase event carries its item's `created_at`, so it can land up to 4 days after the
  session's views. That is why 11% of sessions span two or more UTC dates.

## What the pipeline does about it

| Finding | Handling |
|---|---|
| Item `created_at` unreliable and sometimes in the future | Sales are dated by the order's `created_at` (contract v1) |
| Future-dated items and events | Ingestion windows end at the run's `as_of`, and the watermark is the previous run's `as_of`, never the max `created_at` seen |
| Status updates, returns (within 10.7 days) and late purchase events (within 4 days) after the order | Re-read a 14-day lookback window each run; the contract marks those days as restatable |
| Nullable keys | Not-null and uniqueness checks on every primary key |
| History regenerated by each daily refresh | `make run` uses `--full-refresh`; incremental runs refuse to continue if the history outside the window changed |
| Sessions across midnight | Documented approximation in [contract.md](contract.md) |
